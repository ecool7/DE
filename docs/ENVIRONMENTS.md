# Стенды: TEST и PROD

В банке код и витрины **не катают сразу в прод**. Сначала тест → проверка → релиз.

В этом учебном проекте то же самое, только локально на диске.

## Два стенда

| Стенд | Путь | Для чего |
|-------|------|----------|
| **test** | `stands/test/` | Ты пишешь ETL, ломаешь, чинишь, смотришь данные |
| **prod** | `stands/prod/` | «Боевые» данные для бизнеса. Меняешь **только релизом** |

```
stands/
├── test/
│   ├── data/raw|staging|curated
│   └── run_logs/          ← логи запусков пайплайнов
├── prod/
│   ├── data/raw|staging|curated
│   └── run_logs/
└── releases/              ← манифесты релизов (кто, когда, что промоутнул)
```

## Правило

1. Работаешь **только в test** (`RSHB_ENV=test`, так по умолчанию).  
2. Когда готово — прогон + проверка в Ops Console.  
3. Релиз: `python scripts/release_to_prod.py --entities clients --business-dt YYYY-MM-DD`  
4. Смотришь **prod** в Ops Console — данные появились.

Прямо руками править файлы в `stands/prod/` — антипаттерн (как SSH на прод-сервер без заявки).

## Визуально смотреть сервис

Да, можешь. Есть **Ops Console** — маленькое веб-приложение (Streamlit).

```bash
.venv\Scripts\activate
streamlit run apps/ops_console/app.py
```

Откроется браузер (обычно http://localhost:8501):

- статус test / prod  
- какие файлы лежат, сколько строк  
- логи запусков  
- история релизов  

Это не «сайт банка», а **операционная панель дата-инженера** (упрощённый аналог мониторинга пайплайнов).

## Переменная окружения

```powershell
$env:RSHB_ENV = "test"   # по умолчанию
$env:RSHB_ENV = "prod"   # только читать / смотреть; писать — через release
```

Скрипты читают env из `configs/envs/{test|prod}.yml`.
